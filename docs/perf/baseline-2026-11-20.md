# Production API Performance Baseline — 2026-11-20

Baseline latency and resource measurements of the metaso-p2p production API surface
(`so.metaid.io` / `socket.metaid.io`), taken before the planned large-scale promotion.
Purpose: record the current state and drive the P0 optimization rounds that follow.

- Measurement date: 2026-11-20 (production commit `28188ee`, service active/running, 0 restarts)
- Method: read-only sequential sampling; no load test was performed against production
- Raw data: 7 samples per endpoint, sequential, cold connections (each sample includes DNS + TCP + TLS)

## Measurement setup

Two vantage points, same parameters and sample IDs (real corpus data):

1. **Public side** — from a client machine through Caddy to `https://so.metaid.io` /
   `https://socket.metaid.io`. Includes DNS + TLS handshake + Caddy + network RTT.
2. **Server-internal side** — SSH to `47.242.16.22`, curl directly to
   `172.17.0.1:8088` (main service) and `172.17.0.1:8089` (agentpedia-l2).
   The internal p50 is effectively **pure application processing time**.

Public minus internal ≈ network/Caddy overhead (≈60–200 ms for cold connections,
dominated by TLS; keep-alive clients sit lower). Reported numbers are magnitude
references from a single geographic vantage, not SLA figures.

## Additional production findings

1. **`file.metaid.io` does not resolve on the production host** — systemd-resolved
   (`127.0.0.53`) returns NXDOMAIN while public resolvers resolve the name fine
   (CNAME to `file.metaid.io.a1.initaf.com`, CDN). Effect: the userinfo remote
   profile fallback is dead on production — 227 error lines in one hour — and
   every profile-miss path pays a doomed DNS lookup before failing.
2. **Rate limiting covers only the `/api` group** — `/chat-api` (which hosts the
   heaviest endpoint, `online-users`) and the root-level `notify` aliases are not
   rate-limited. This matters before promotion.
3. **Full-scan-then-paginate patterns** exist across groupchat chat lists
   (`collectGroupRootMessages` full namespace scan + JSON unmarshal per page),
   qa answers feed, mrc721 sell/offer/collection lists, and mrc721nft
   `collection/pageList` (offset pagination rescans from the start). All are
   fast at current data volume (<50 ms) but their cost grows linearly with the
   corpus — chronic risk as promotion drives ingestion.
4. Chat-list endpoints return **237 KB for size=20** — a mobile/weak-network
   payload concern independent of server time.

## Optimization plan (P0 rounds)

1. **P0-1 `online-users`**: TTL snapshot cache (1–2 s) for the presence+profile
   response; profile hydration from the local Pebble store only (skip the doomed
   remote fallback on the hot path).
2. **P0-2 DNS**: stop the bleeding on `file.metaid.io` resolution (hosts entry or
   resolver fix); provider-side DNS hardening tracked separately by the domain owner.
3. **P0-3 `bots/search` and `metaweb/search`**: corpus/snapshot caching so repeated
   queries do not rescan the full corpus per request.
4. **P1 backlog**: materialized follow counts, chat-list pagination pushdown into
   Pebble, payload slimming, `/chat-api` rate-limit coverage.
